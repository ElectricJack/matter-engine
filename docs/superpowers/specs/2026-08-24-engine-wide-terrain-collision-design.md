# Engine-Wide Authored-Region Terrain Collision

Date: 2026-08-24

Status: Design approved in conversation; awaiting written-spec review

## 1. Purpose

Matter Engine renders procedurally generated volumetric terrain and uses the
same final terrain field, including the accepted river height overlay, as an
input to fluid baking. Dynamic Box3D bodies currently receive no collision
representation for that terrain. They can collide with explicitly authored
crate, raft, and boulder shapes, and river forces can make them float, but the
rendered riverbed and banks do not exist in the Box3D world.

This feature adds engine-wide terrain collision generated by the existing CPU
terrain mesher. Worlds opt in by declaring one or more bounded collision
regions. One world-level collision resolution applies to every region. The
visual terrain LOD and collision resolution remain independent.

The first acceptance world is `RiverFloatLab`. Its crates and rafts must float,
contact the carved bed and banks, strike authored boulders, and pass over
sector boundaries without gaps or hidden proxy walls.

## 2. Goals

- Generate collision from the exact final `terrain_field::FieldRuntime` used by
  terrain rendering, including `RiverHeightOverlay` carving.
- Support volumetric surfaces such as cliffs, caves, and overhangs through
  static triangle meshes rather than height fields.
- Restrict collision to explicit authored world-space regions.
- Use one deterministic, configurable collision cell size for the entire
  world.
- Reuse the existing CPU `terrain_mesher`; do not create a second terrain
  representation or derive collision from a GPU readback.
- Build and cache collision off the frame-critical path.
- Install one complete collision generation into Box3D before Play can begin.
- Keep the Box3D mesh resources alive for exactly the lifetime of the installed
  collision generation.
- Leave worlds that do not author terrain collision byte-for-byte and
  behaviorally unchanged.
- Reduce only RiverFloatLab's crate visual/collider from 3 m to 1.5 m.

## 3. Non-goals

- Making all infinite rendered terrain collidable.
- Generating hidden box, ramp, or wall proxies.
- Treating the water surface as a rigid collider.
- Replacing authored boulder colliders or general scene rigid bodies.
- Using visual GPU mesh buffers as the authoritative physics source.
- Supporting different collision resolutions in different regions of one
  world.
- Runtime terrain deformation or incremental collision edits in this version.
- A general authored arbitrary-triangle `MeshCollider` component in scene
  recipes. Terrain collision is owned by the world/terrain pipeline.

## 4. Imperative DSL

The authoring shape follows the existing imperative builder convention. A new
optional world instance hook, `collision()`, is evaluated in a dedicated
collision-authoring phase after the ordinary world definition has been parsed:

```js
class RiverFloatLab extends World {
  collision() {
    const collision = terrainCollision({
      cellSize: 0.5,
      friction: 0.72,
      restitution: 0.02,
    });

    collision.region("river-gameplay", {
      min: [-64, -64, -64],
      max: [384, 128, 64],
    });

    collision.build();
  }
}
```

Omitting `terrainCollision()` means the world has no generated-terrain
collision, preserving current behavior. A world may create only one builder
and call `build()` once. At least one region is required when the builder is
present. `terrainCollision()` is legal only while the loader is evaluating
`collision()`; use from module scope, `field()`, `hydrology()`, `biomes()`, or
`buildEntities()` fails with a phase-specific diagnostic. A `collision()` hook
that returns without one completed builder is also invalid.

`cellSize` is the one resolution for every region. It must be one value from
the deterministic terrain-mesher ladder:

```text
0.25, 0.5, 1, 2, 4, 8, 16, 32, or 64 metres
```

These values map exactly to terrain-mesher rungs 3 through -5. Arbitrary
floating-point resolutions are rejected rather than rounded silently.

`cellSize` is required. `friction` defaults to `0.7` and must be finite and lie
in `[0, 1]`. `restitution` defaults to `0.0` and must be finite and lie in
`[0, 1]`. They apply uniformly to every generated terrain shape in the world.

Region ids are non-empty and unique. `min` is inclusive, `max` is exclusive,
all values are finite, and each `min` component is strictly less than its
matching `max` component. Bounds must align to the world's base sector grid in
X, Y, and Z. Misaligned bounds fail validation; the engine never silently
expands collision outside the authored area.

Multiple regions may overlap. The builder canonicalizes their union into one
sorted set of sector coordinates, so an overlapping sector is meshed, cached,
and installed exactly once. Region names remain diagnostic labels and do not
create duplicate geometry.

## 5. Public and internal data boundaries

`WorldDefinition` gains an optional provider-neutral
`TerrainCollisionDefinition` containing:

- global cell size/rung;
- global friction and restitution; and
- the validated authored region records.

The loader and native builder expose no Box3D, renderer, Vulkan, or Flecs types.
Canonicalization produces a sorted unique sector-coordinate set from the
region union.

The collision geometry boundary is an immutable engine-native candidate:

```text
TerrainCollisionCandidate
  generation key
  global material settings
  sorted TerrainCollisionTileCandidate[]
    sector coordinate
    sector origin
    finite local positions
    triangle indices
    tile digest
```

The candidate contains ordinary CPU geometry only. Worker code cannot call
Box3D. The physics-owner thread converts an accepted candidate into the private
Box3D runtime representation.

## 6. Geometry generation

For each sector in the canonical union, the worker calls the existing
`terrain_mesher::mesh_sector_tiled` with:

- the installed final `terrain_field::FieldRuntime`;
- the exact `RiverHeightOverlay` already attached to that runtime;
- the authored base sector size;
- the world-global collision rung; and
- the sector's X/Y/Z coordinate.

This is a second product from the same field semantics, not a second mesher.
Visual terrain may use camera-dependent nested-sector LOD and GPU meshing;
collision always uses its authored fixed rung and the deterministic CPU oracle.

All material buckets contribute terrain triangles. Render materials do not
change collision identity except where they change the final density/geometry.
Optional seam-boundary and overlap-band rendering geometry is not installed as
collision. Every collision sector uses the same rung, so the terrain mesher's
shared dyadic lattice and equal-rung ownership rule are the authority for
sector continuity.

An all-air or all-solid sector is a successful empty tile and creates no
Box3D shape. Non-finite vertices, out-of-bounds indices, invalid winding,
unapproved degenerates, numeric overflow, or a failed terrain sample reject
the complete candidate.

The conversion step deterministically welds bit-identical tile-local vertices,
preserves outward winding, and feeds indexed triangles to Box3D's static mesh
API. Box3D mesh collision is never attached to dynamic or kinematic bodies.

## 7. Cache identity and persistence

Collision cache identity is independent of visual-only settings. Each tile key
contains:

- canonical final field-program identity;
- river overlay/carve identity, if present;
- terrain-mesher semantic version;
- sector size and exact sector coordinate;
- the single collision rung/cell size; and
- collision-geometry format version.

Friction and restitution belong to the generation manifest and Box3D shape
installation identity, but they do not force triangle remeshing. Region names
are excluded from tile geometry keys. The canonical sector union determines
which tile products the generation requires.

Tiles are immutable content-addressed products, allowing bounds changes to
reuse unchanged sectors. A generation manifest references the exact sorted tile
set and material settings. Publication follows the repository's retained-file,
validate-before-use, immutable-manifest conventions.

A corrupt or missing tile receives one clean rebuild attempt from the canonical
field. If rebuild or validation fails, the candidate fails. No stale tile,
partial generation, or render-mesh substitute is accepted.

## 8. Installation and lifetime

CPU meshing, exact welding, validation, digesting, and persistence run on the
world-build worker. Creation and destruction of Box3D objects run only on the
physics-owner thread at a safe pre-step boundary.

The private `TerrainCollisionRuntime` owns, per non-empty tile:

- the retained Box3D mesh data;
- one static body;
- one static mesh shape; and
- the candidate generation/tile identity used for diagnostics.

Construction is transactional. The installer validates and creates a complete
replacement runtime. If any tile fails, it destroys every object created for
that candidate and leaves the prior accepted runtime untouched. A successful
install swaps the complete runtime once. Only after the swap may the new world
report Ready or enter Play.

Destruction order is shape/static body first, retained mesh data second. World
reload and unload clear every terrain collision object before the owning
physics world is destroyed. The physics fixed step never observes a mixture of
old and new terrain generations.

There is no runtime remeshing, GPU readback, or per-tick terrain-collision
allocation in this version.

## 9. Failure and diagnostics

Authoring errors report the builder path and offending field, for example:

```text
terrainCollision.cellSize must be one of the supported terrain rungs
terrainCollision.region[river-gameplay].max must be sector aligned
```

If a world declares terrain collision, it is required gameplay data. Build,
cache-validation, or Box3D installation failure prevents that candidate from
reaching Ready. The engine must not continue with rendered but non-colliding
terrain.

Editor/world diagnostics expose:

- generation key and status;
- configured cell size/rung;
- authored region count and canonical sector count;
- non-empty/empty tile counts;
- triangle and unique-vertex counts;
- artifact bytes and Box3D retained bytes;
- cold-build, cache-load, validation, and install times; and
- the first precise failure code/message.

A debug visualization may outline authored region bounds and installed tile
bounds, but it is diagnostic only and never becomes collision geometry.

## 10. RiverFloatLab integration

RiverFloatLab authors one engine terrain-collision builder at `0.5 m` and a
sector-aligned region covering the complete accepted upper/lower ravine,
waterfall, pools, spillways, banks, and reasonable escape margin. It does not
enable collision for the rest of the streamed world.

The shared 3 x 3 x 3 m `projects/world_demo/objects/Crate.js` remains unchanged.
RiverFloatLab gains a scene-local `RiverCrate` part measuring exactly
1.5 x 1.5 x 1.5 m. Every RiverFloatLab crate recipe uses:

```text
PartInstance: RiverCrate
BoxCollider.halfExtents: [0.75, 0.75, 0.75]
```

Its equilibrium spawn height is recomputed from the new collider dimensions
and existing authored density. Raft dimensions and colliders remain unchanged.
Explicit boulder rigid bodies remain because they are separate authored scene
objects, not generated terrain.

## 11. Verification

Implementation follows test-driven development. Every C/C++ build and test uses
the repository MSVC wrapper and Visual Studio CTest tree. Make, GCC, g++,
MinGW, MSYS/UCRT, `collect2`, and stale legacy executables are prohibited.

### DSL and identity tests

- builder omission preserves the prior world definition;
- one valid builder with one and multiple regions canonicalizes deterministically;
- duplicate build, missing regions, duplicate ids, non-finite data, bad ranges,
  unsupported cell sizes, and non-sector-aligned bounds fail precisely;
- overlapping regions produce one sorted unique sector set;
- region order and overlap decomposition do not affect geometry identity;
- cell-size, final field, carve, bounds union, and mesher-version changes
  invalidate the appropriate identity;
- friction/restitution changes reuse geometry but replace installation identity.

### CPU geometry tests

- a flat field, steep slope, rounded riverbed, cave, cliff, and overhang produce
  valid deterministic collision tiles;
- collision geometry is byte-repeatable and uses the same final field/overlay
  as the visual terrain path;
- all-air/all-solid sectors succeed empty;
- non-finite samples, overflow, invalid triangles, and corrupt cache data fail
  closed;
- equal-rung neighboring sectors are watertight at their shared planes.

### Box3D integration tests

- dynamic boxes and flattened rafts settle on flat, sloped, and carved terrain;
- bodies contact cave ceilings and overhangs, proving this is not a height field;
- continuous high-speed bodies do not tunnel through the terrain;
- bodies cross X/Y/Z sector boundaries without falling through, snagging,
  explosive impulses, or duplicate-contact instability;
- terrain shapes are static, use the authored material settings, and participate
  in the existing collision filters;
- failed candidate installation leaves the prior generation intact;
- successful replacement is atomic and unload destroys all retained Box3D
  mesh resources with no leaks;
- steady fixed ticks perform no collision remeshing or terrain-runtime allocation.

### RiverFloatLab acceptance

- Node scene tests prove the one 0.5 m collision definition and bounded region;
- all crate parts/colliders are exactly 1.5 m/0.75 m while other worlds retain
  the shared 3 m Crate;
- the PhysX-enabled MSVC editor cold-builds RiverFloatLab with zero errors;
- a second run is a collision-geometry cache hit and performs no tile remeshing;
- diagnostics record triangle count, memory, cold/cache timings, and install time;
- visible Play-mode screenshots and direct observation show crates and rafts
  floating, contacting the bed/banks, striking boulders, and continuing across
  terrain-sector boundaries.

The existing automated river-traversal CSV seam remains a separate deferred
proof concern. Terrain collision acceptance does not fabricate that telemetry.
