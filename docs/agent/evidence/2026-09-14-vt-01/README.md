## Owner-scoped input updates

The ordinary renderer material/source push and surface-update bracket now select dependent VT owners instead of calling `invalidate_all_content()`:

- Residency maintains reverse material-to-owner links through registration, shared aliases, surface edits, removal of classifications, and final owner release. Chart-stream triangle material IDs and scalar fallbacks use the same first-corner selection and 8-bit transport as the compositor. Tape palettes retain the conditional triangle fallback because zero evaluated weights can select it.
- Renderer input comparison uses the compositor's effective albedo/ORM/detail-slot fields. Revision-only publications and changes to other material fields do not rewrite VT inputs. Appended, edited, or removed materials select only their live consumers; source-slot load/unload revisions select materials referring to the old or new slot.
- Surface updates report whether accepted inputs actually changed. Identical publications do not invalidate pages or prepared buffers. Changed aliases coalesce to one physical owner in the update bracket. Removing a tape removes obsolete palette links and retains triangle-material fallback links.
- Dependencies use a 256-ID scratch mask, avoiding a temporary material list proportional to triangle count. Reverse links disappear at final owner release.

The implementation still waits for existing shared compositor buffers/descriptors before changing them, and still drops affected owners' detail mappings while scheduling their tail refreshes. These are V3 limitations. This step proves scoped dirtiness; it does not prove flicker-free replacement, safe asynchronous snapshots, spatial page bounds, or zero ordinary idle waits.

`scoped-native-checks.json` records native commands/exits for `vt-queue`, `vt`, `vt-surfaces`, `vt-enrich`, `vt-normal-frame`, and `surface-parallax`: all exit 0, report `ALL PASS`, and report zero Vulkan validation errors. `scoped-tests-source.json` fingerprints the test binary and relevant sources. The expanded production-queue fixture checks independent owners, compatible aliases, unused IDs, conditional scalar fallback, surface palette changes/removal, and identical publications. Real renderer tests also advance a material revision, append an unused material, and edit it while asserting no page fills/invalidations and unchanged sampled GPU albedo. Existing renderer material edits still update the intended pixels.

Still open in V2: spatial page selection and conservative border/ancestor expansion, dedicated source replacement/failure cases, and broader alias/consumer coverage. No phase exit gate is closed by this partial implementation.

## Candidate publication and durable replacement work

The production residency layer now retains dirty resident pages and their mappings, uses 64 scratch slots inside the existing physical pool, and copies candidates into final slots only after successful recording and owner/content/slot generation validation. Scratch is disjoint from resident and retiring slots. GPU transfer dependencies order the final copies after preceding readers and before subsequent sampling. Old page addresses remain stable; a failed or superseded candidate never writes the resident slot. Dirty work is bounded by occupied slots and survives trimming of the execution queue. Initial coverage retains the existing readiness gate. Pending enrichment is skipped for dirty pages and is renewed after successful base replacement.

The reserve is explicit: 64 × 129,472 bytes = 8,286,208 bytes (7.90234375 MiB), included in the configured pool bytes. Usable resident capacity is physical capacity minus 64; no extra pool image is allocated. The 512-slot pressure fixture therefore has 448 usable slots, while the 33,024-slot reference configuration has 32,960. This is replacement headroom, not a reduced texel density or POM setting. Traversal/quality and timing acceptance still need to demonstrate the full workload with this effective capacity.

The new GPU fixture uses the shipped page writer and exact auxiliary-byte readback. Its producer deliberately writes then refuses, supersedes its revision after recording, or releases its owner after recording. `vt-candidate-red.log` reproduces three old failures with zero Vulkan validation errors: dirtiness destroys detail mappings, a refused producer changes current pixels, and detail does not retry without feedback. Red test exit 1; `candidate-red-source.json` records its source/binary identity. The first red fixture build failed on a missing preferred-memory argument; the corrected red build succeeds (`build-vt-candidate-red-retry.log`). That compile failure was not counted as a behavioral regression result.

`vt-candidate-green.log` exits 0 with `ALL PASS` and zero validation errors. The existing 300-owner burst and sustained-feedback pressure cases also pass; the usable pool fills completely, duplicate refreshes coalesce, and every required replacement drains without destructively dropping resident pages. The expanded `vt-candidate-readers.log` also exits 0 with zero validation errors. It records an old readback, replacement, and new readback in one GPU submission, using distinct staging-ring slots for the two frame records and no intermediate CPU wait: old readers receive the old bytes, later readers receive the new bytes. Both logs retain the existing scoped-dependency and retry-age checks.

The final candidate rendering suite passes all six native modes with validation enabled: `vt-queue`, `vt`, `vt-surfaces`, `vt-enrich`, `vt-normal-frame`, and `surface-parallax`. `candidate-regression-checks.json` records exact commands, exits 0, and individual logs; every log reports zero validation errors. `build-vt-candidate-verified.log` records a successful incremental build after the prior build handle was unavailable at continuation. All 11 Python analyzer tests pass (`vt-candidate-analyzer-final-tests.log`). Subsequent compositor-input work and its separate rerun follow below.

This is **partial V3 evidence**. Shader-visible material/source snapshots are not yet versioned with page publication, source-image ownership still uses its previous discipline, spatial page bounds are not yet implemented, and asynchronous worker-job ownership remains V4 work. These tests establish producer/publication isolation, not complete flicker-free POM/source replacement or performance acceptance.

## Remaining acceptance work

### Memory density question

The first instrumented castle trace reports 33,024 physical slots and 4,077.609375 MiB of format-accounted pool image storage. At `settle_end`, 1,469 slots are occupied (4.45%, 181.3835 MiB of slot capacity); at `return_end`, 2,327 are occupied (7.05%, 287.3243 MiB). Both include 79 pinned tails (9.7545 MiB). Thus 92.95–95.55% of pool capacity is unused in these two views. The corrected-camera capture ends with 1,717 occupied pages (5.20%, 212.005 MiB); `castle-memory-density.json` records its exact byte breakdown and explicitly leaves triangle coverage unknown. These are unused reserved capacity measurements, not the working set needed for all terrain traversal.

The fixed-camera terrain baseline occupies 1,631 pages (201.3863 MiB, 4.94%) when settled and 2,153 pages (265.8398 MiB, 6.52%) after turning away and returning. Thus 93.48–95.06% of the same pool capacity remains unused across that path. Its 789 pinned tails reserve 97.4211 MiB of slots. This is still a narrow view/turn experiment, not an exhaustive traversal working set. `stream-memory-density.json` records the original format-level calculation; the later geometric diagnostic below measures triangle coverage separately.

The layout is a gapless 16×16 slot grid per array layer. A slot stores 136×136 texels around a 128×128 payload: physical borders are 11.4187% of slot bytes, or 12.8906% extra relative to payload alone. BC7 albedo, BC5 normals, and BC7 ORM cost one byte per texel each; RGBA8 material IDs/blend cost four, totaling 129,472 bytes (126.4375 KiB) per slot. Metadata therefore accounts for 57.14% of pool format bytes. The compositor writes its fourth auxiliary lane as constant 1; reclaiming it requires checking consumers and supported alternative formats/packing, not simply compressing material IDs with a lossy color codec.

Source: `MatterEngine3/src/render/vt_types.h` physical layout/channels, `chart_atlas.h` payload/borders, `vt_residency.cpp` pool sizing, `shaders_vk/vt_composite.comp` auxiliary output, and `libs/MeshChartingLib/src/mesh_charting.cpp` page-aligned shelf packing. Each chart's content plus gutters rounds up to whole pages at mip zero. Thin/small/irregular charts can therefore waste texels within occupied pages. These initial captures did not measure triangle coverage; the follow-up below adds that diagnostic separately from timing captures. Spare pool capacity, chart gaps, page borders, and channel representation must not be conflated or added as if they were independent percentages of the same denominator.
